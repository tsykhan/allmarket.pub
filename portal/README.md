# allmarket.biz Seller API — серверна частина порталу

Реалізація контракту [allmarketsync/docs/API.md](../allmarketsync/docs/API.md) на боці порталу
allmarket.biz. API — окремий PHP-код у `/api/v1/`, який напряму працює з таблицями
порталу і не завантажує ядро. Сторінка продавця — вкладка «Інтернет-магазин» у розділі кабінету
«Інтеграції» (`integrations.php?kind=shop&action=shopapi`); характеристики товарів пишуться через
модуль порталу «Характеристики» (`module/multitrade/features.api.php`).

PHP 7.2+ (продакшн — 8.4, перевірено на 7.4 і 8.4), розширення mysqli, curl, dom, mbstring.

## Що куди пише

| API | таблиці порталу |
|---|---|
| `/products/batch` | `all_multitrade` (товар «Мегамаркету», модуль 23) + `all_multitrade_data` (опис) |
| `/products/batch` → `attributes` | `all_mtf_product*` через `features.api.php`; за потреби нові записи в `all_mtf_feature`/`_value`/`_i18n`, відповідності в `all_mtf_xref` |
| `/offers/batch` | `all_multitrade.price`, `.amount` (без зміни `edittime`, щоб не піднімати товари в стрічці) |
| `/products/delete` | `all_multitrade.status = 0` (у кошик, не видаляється); повторне вивантаження повертає товар |
| `/categories/batch` | лише власна таблиця `all_amapi_category` |
| `GET /orders` | читає `all_multitrade_order` (seller = продавець), `all_member` (email покупця) |
| `/orders/{id}/ack` | лише `all_amapi_order` |
| `/orders/{id}/status` | `all_multitrade_order.status`, `send_no`, `send_type`, `send_time` (див. нижче) |

Власні таблиці (створюються автоматично при першому запиті, InnoDB): `all_amapi_seller` (ключі,
налаштування), `all_amapi_item` (external_id ↔ itemid), `all_amapi_category`, `all_amapi_order`
(ack, вебхук), `all_amapi_log` (журнал запитів, 30 днів). Таблиці порталу не змінюються (ALTER немає).

Правила відповідності:

- Одна позиція (`external_id`) = один товар `all_multitrade`. Комбінації — окремі товари з тим самим `group_id` (зберігається в `all_amapi_item`).
- Категорія порталу: `allmarket_category_id` позиції → відповідність категорії магазину з `/categories/batch` → категорія за замовчуванням продавця (кабінет) → інакше `error: category is required`. Дозволені лише категорії модуля 23.
- Текстові поля зберігаються HTML-екранованими (як це робить VuCMS), опис — через білий список тегів (без script/iframe/on*-атрибутів, `javascript:`-посилань). Символи поза BMP (емодзі) вирізаються — таблиці в utf8.
- `keyword` = «назва,бренд,шлях категорії» — так його формує VuCMS для пошуку.
- Контакти продавця (компанія, телефон, адреса, VIP, регіон) копіюються з `all_member`/`all_company`, як при ручному додаванні.
- Статус нового товару — `item_status` з конфігурації (3 = опубліковано, 2 = на модерацію). Рішення модератора (1/2) при оновленні не перезаписуються.
- **Ціни** зберігаються в обліковій валюті продавця (Кабінет → Валюти → `company.currency`; порожньо — валюта порталу
  `money_unit_rate`, USD): саме в ній портал показує `multitrade.price`. Ціна з магазину в іншій валюті перераховується
  за ручним курсом продавця (`fx_manual`) або ринковим курсом порталу (`all_fx`). Щоб ціни переходили без перерахунку,
  облікова валюта продавця має збігатися з валютою вивантаження модуля (зазвичай UAH). `/ping` повертає `shop.currency`.
- **Залишок** — справжня кількість; позиція «в наявності» з кількістю 0 (замовлення без залишку) → `backorder_amount` (0).
- **Розміщення** задає продавець у модулі (панель «Розміщення категорій»): `allmarket_category_id` — категорія магазину
  є цією категорією порталу; `allmarket_parent_id` — створити її всередині цієї категорії. `GET /portal-categories`
  віддає модулю дерево категорій Мегамаркету (назви мовою `content_lang`, шлях, глибина, кількість товарів).
  Категорії, створені API, записуються в `all_amapi_created`: при зміні розміщення API **переносить** їх (а не створює
  нові), товари розділу магазину переходять у нову категорію без повторного вивантаження, а непотрібні порожні
  створені категорії видаляються (`AmCategories::cleanup`). Категорії, створені не API (адміном), не переносяться й не видаляються.
- **Категорії** (`create_categories`, увімкнено): `/categories/batch` розкладає дерево магазину на категорії Мегамаркету.
  Явна відповідність з модуля (відмінна від батьківської) має пріоритет; інакше категорія шукається за назвою серед
  підкатегорій батьківської портальної категорії і, якщо її немає, створюється так само, як у адмінці (catdir, linkurl
  `<catdir>-<id>-1.html`, arrparentid/arrchildid, права груп від батьківської), після чого оновлюється кеш
  `file/cache/category-23.php` і дерева. Товар іде в найточнішу категорію свого розділу магазину. Лічильники `item`
  рахуються з підкатегоріями й по мовах, як «Оновити статистику».

### Характеристики (`attributes` → «Характеристики» порталу)

`lib/AmFeatures.php` викликає `mtf_api_feature_ensure` / `mtf_api_product_set` з `module/multitrade/features.api.php`.
Для цього API піднімає лише потрібні шматки ядра: `system/db_mysqli.class.php` + `system/db.class.php` (фасад `DB`),
`VCM_ROOT`/`VCM_PRE`, `$VCM_LANGS` з `file/cache/langs.php` і `content_langs()` (копія з `system/global.func.php`).

- Відповідність id PrestaShop → довідник порталу в `all_mtf_xref` (engine `prestashop`). Таблиця спільна для всіх
  продавців, тому id мають префікс продавця: `u<userid>:f<id_feature>`, `u<userid>:fv<id_feature_value>`,
  `u<userid>:a<id_attribute_group>`, `u<userid>:av<id_attribute>`.
- Без id (старий модуль, PrestaShop 1.6 для значень) характеристика й значення шукаються за назвою серед
  глобальних і власних характеристик продавця — так само, як у формі товару кабінету.
- Нове створюється як власне продавця (`userid` = продавець) і лише якщо в налаштуваннях порталу `seller_own=1`;
  з `moderation=1` нові характеристики йдуть на модерацію (API викликає з `trusted=false`).
- Тип нової характеристики — `select` (кілька значень однієї характеристики → `multiselect`); значення
  `custom: true` пишеться як власне значення товару. Якщо назва збіглася з наявною характеристикою іншого типу
  (`number`, `text`, `bool`, `date`), значення приводиться до цього типу (`"0,3 кг"` → 0.3).
- Картка з магазину — джерело правди: при кожному оновленні характеристики товару замінюються повністю.
- Якщо модуля «Характеристики» немає або він вимкнений (`all_setting features.on=0`), або `config['features']=false`,
  атрибути, як і раніше, додаються таблицею в опис.

### Замовлення

API-замовлення = рядок `all_multitrade_order` (одна товарна позиція), `id = "AM-<itemid>"`.
У магазин передаються лише замовлення, оформлені **після створення першого ключа** (`orders_from`).

| портал `status` | API `status` | `paid` |
|---|---|---|
| 0 оформлено | new | ні |
| 1 продавець підтвердив, 10 очікує підтвердження оплати | accepted | ні |
| 2 оплачено | processing | так |
| 3 доставлено, чекає покупця | shipped | так |
| 4 угода завершена, 7 виплачено продавцю | delivered | так |
| 5 запит повернення / 6 кошти повернуто | returned | 5 — так |
| 8 / 9 закрито покупцем / продавцем | cancelled | ні |

Зі статусів магазину автоматично застосовуються лише переходи, що **не рухають гроші** (escrow порталу):
`accepted` (0→1), `cancelled` (0/1→9, залишок повертається на товар), `shipped` (2→3 + ТТН, перевізник, дата).
ТТН записується і без зміни статусу. Інші переходи лише фіксуються: відповідь `200 {"ok":true,"applied":false,"message":…}`,
щоб модуль не повторював їх безкінечно.

### Вебхук (портал → магазин)

`api/v1/cron.php` раз на хвилину надсилає продавцям з URL вебхука нові (`order.created`) і змінені
(`order.updated`) замовлення з підписом `X-Allmarket-Signature: sha256=HMAC(тіло, секрет)`.
Відповідь `200 {"ok":true,"result":"imported|skipped|updated"}` = ack. Помилки — до `webhook_max_tries`
спроб на версію замовлення; останній результат видно в кабінеті. Вебхуки лише на публічні адреси.

## Встановлення на сервер

1. Скопіювати в корінь сайту (httpdocs), нічого не перезаписуючи:
   ```
   api/v1/                     → httpdocs/api/v1/
   member/allmarket_api.php    → httpdocs/member/allmarket_api.php   (стара адреса → редирект у «Інтеграції»)
   ```
   `api/v1/.htaccess` закриває `lib/`, `config*.php`, `cabinet.*` і передає заголовок `Authorization` у PHP (FastCGI/FPM).
2. Вкладка «Інтернет-магазин» у «Інтеграціях» — скриптом (спершу без `--apply`, він лише перевіряє):
   ```
   /opt/plesk/php/8.4/bin/php install/integrations_patch.php /var/www/vhosts/allmarket.biz/httpdocs
   /opt/plesk/php/8.4/bin/php install/integrations_patch.php /var/www/vhosts/allmarket.biz/httpdocs --apply
   ```
   Він робить 4 вставки (рядок у `$INT_KINDS`, `case "shopapi"` у `module/member/integrations.inc.php`; сторінку й
   картку в `template/b2b-b2c/member/integrations.htm`), кожну за якорем, що має трапитися рівно раз (перевірено на
   поточних файлах продакшну, лише читанням), зберігає копії `*.amapi-bak-<дата>` і повторно нічого не змінює.
   Окремого пункту меню не треба: «Інтеграції» вже є в меню кабінету. `template_refresh=1` — шаблон перекомпілюється сам.
   Вкладка доступна групам із правом `shop` (як і весь розділ «Інтеграції»).
3. Налаштування — `api/v1/config.local.php` (повертає масив з ключами `config.php`), наприклад `item_status`, `currencies`, `cron_token`.
4. Cron: `* * * * * /opt/plesk/php/8.4/bin/php /var/www/vhosts/allmarket.biz/httpdocs/api/v1/cron.php` (Plesk → Заплановані задачі).
   Саме цей шлях: `php` у командному рядку сервера — 5.6, на ньому код не запуститься (потрібен PHP 7.2+). Без CLI — `cron_token` і URL `https://allmarket.biz/api/v1/cron.php?token=…`.
5. Перевірка: `https://allmarket.biz/api/v1/` → `{"ok":true,"service":"allmarket.biz Seller API","version":1}`;
   у кабінеті «Інтеграції» → «Інтернет-магазин» → «Підключити» → «Створити API-ключ» → URL, ID і ключ у модуль PrestaShop → «Перевірити з'єднання».

DB-реквізити API читає з `httpdocs/dbvucmsconf.inc.php` (як ядро). Потрібні права CREATE (власні таблиці) і
SELECT/INSERT/UPDATE на таблиці порталу.

## Staging і тести

`tools/staging/up.sh` піднімає копію: MariaDB із резервної копії VuCMS (`file/backup/…/*.sql`) +
PHP 7.4/Apache з цим кодом, у мережі `amtest` поруч із тестовим PrestaShop:

```
DUMP_DIR="…/httpdocs/file/backup/2017-04-19 21.48.49 uwahlpeler" tools/staging/up.sh
docker exec amportal-web php /var/www/html/staging/issue_key.php lateralus 9   # ключ для продавця, категорія за замовч.
```

Кабінет без ядра VuCMS: `http://localhost:8090/staging/cabinet.php?user=lateralus` (лише staging; та сама
сторінка, що й у «Інтеграціях», з тимчасовими стилями замість стилів шаблону b2b-b2c).
`config.staging.php` дозволяє EUR (у демо-PrestaShop немає UAH).

`tools/staging/core/` — копії файлів ядра продакшну, потрібних для характеристик (`system/db*.class.php`,
`module/multitrade/features.api.php`, уривок `features.lib.php` лише з функціями запису/читання значень,
`file/cache/langs.php`), а `prod_schema_additions.sql` — DDL таблиць `all_mtf_*`, `all_ubrand` і колонки
`ubrandid` з продакшну (копійовано лише читанням 2026-10-16). Лише для staging, не встановлювати.

Перевірено проти staging з модулем allmarketsync (PrestaShop 8.2.8): повне вивантаження 47 позицій
(7 категорій, 11–12 груп комбінацій), дельта ціни/залишку, зняття вимкненого товару й повернення,
відхилення позицій (валюта, ціна, категорія), імпорт замовлень (накладений платіж і оплачене),
ack і відсутність повторів, статуси магазину → портал (accepted 0→1, shipped 2→3 з ТТН),
скасування на порталі → «Canceled» у магазині, вебхук (ping з кабінету, order.created з ack,
order.updated зі зміною статусу, ідемпотентність, невірний підпис), 401 на чужий ключ / ID, 403 для вимкненого продавця.

Характеристики (2026-10-17, свіжий PrestaShop 8.2.8 з демо-даними): 6 характеристик / 22 значення потрапили
в довідник з відповідностями `u1:…` в `all_mtf_xref`; зміна значення й видалення характеристики в магазині
доходять на портал; повторний запуск нічого не надсилає; другий продавець з тими самими id отримує свої
записи; наявна глобальна характеристика типу `number` підхоплюється за назвою (`"1,5"` → 1.5); з вимкненим
модулем характеристик — таблиця в описі. PHP 7.4 і 8.4.

Скрипт `install/integrations_patch.php` перевірено на файлах-замінниках із тими самими якорями (сухий прогін,
застосування, повторний запуск, `php -l`, відмова при відсутньому якорі); на продакшні якорі перевірено лише читанням.

## Порівняння з продакшном (2026-10-16, лише читання)

Схема 6 таблиць (`all_multitrade`, `_data`, `_order`, `all_member`, `all_company`, `all_category`) на продакшні —
надмножина копії 2017 року: колонки лише додані (`multitrade.ubrandid`; у `company` — `lang`, `shoplangs`,
`currency`, `currencies`, `fx_manual`, `co_*`; у `member` — `aid`, `block_shop`, месенджери/соцмережі), жодна не
видалена й не змінила тип. MariaDB 10.5, SQL mode не strict, у користувача БД є право CREATE. Шаблон — `b2b-b2c`,
код ядра на сервері розкодований (`member/*.php` будуються так само, як `allmarket_api.php`).

З цього враховано в коді: артикул пишеться в `multitrade.sku` (на продакшні це артикул, напр. `MA-1377`),
`lang = 'ua-ua'` для нових товарів, `ubrandid` — за назвою зі схвалених брендів довідника `all_ubrand`
(нові бренди API не створює), шаблон кабінету для `b2b-b2c`.

Пізніше враховано: характеристики пишуться через `features.api.php` (див. «Характеристики»), сторінка
API-ключа — вкладка «Інтернет-магазин» у «Інтеграціях» (`install/integrations_patch.php`).

Ще не враховано: переклади (`content_lang`) і валюта компанії (`company.currency`) — API пише лише базові поля
однією мовою (`content_lang`) і приймає ціни у `currencies`.

Не перевірено: вкладка «Інтернет-магазин» усередині справжнього ядра й шаблону b2b-b2c (компілятор шаблонів VuCMS,
стилі) — для цього потрібне встановлення на сервер; на staging ядро не запускається.
