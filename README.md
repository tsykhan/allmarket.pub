# allmarketsync — обмін даними PrestaShop ↔ allmarket.biz

Модуль PrestaShop, який:

- **вивантажує каталог** на портал allmarket.biz: категорії, товари, комбінації (як окремі
  пропозиції з `group_id`), фото, характеристики, бренд, артикул/EAN, вагу;
- **періодично оновлює ціни й наявність** — надсилає лише те, що змінилось;
- **знімає з порталу** товари, які видалили, вимкнули чи виключили фільтрами;
- **імпортує замовлення** з allmarket.biz у PrestaShop (опитуванням або вебхуком) і
  **повертає статуси** та номер ТТН назад на портал;
- додатково формує **XML-фід** (YML-сумісний) для імпорту за посиланням.

Версія 1.1.0 · дві збірки з однаковими можливостями:

| збірка | PrestaShop | PHP | архів | код |
|---|---|---|---|---|
| основна | 1.7.6+ / 8.x | 7.2+ | `allmarketsync-1.1.0.zip` | [allmarketsync/](allmarketsync/) |
| для 1.6 | 1.6.1.x | 5.6+ | `allmarketsync-1.1.0-ps16.zip` | [ps16/allmarketsync/](ps16/allmarketsync/) |

Обидві потребують cURL і XMLWriter і працюють з тим самим API порталу.

## Важливо: API порталу

Публічної документації API в allmarket.biz наразі немає, тому модуль працює за контрактом,
описаним у [allmarketsync/docs/API.md](allmarketsync/docs/API.md). Його треба реалізувати на боці
порталу (ендпоінти `/ping`, `/categories/batch`, `/products/batch`, `/offers/batch`,
`/products/delete`, `/orders`, `/orders/{id}/ack`, `/orders/{id}/status`). Робочий приклад —
мок-сервер [tools/mock_allmarket.php](tools/mock_allmarket.php).

Серверна частина для порталу (VuCMS) — у [portal/](portal/README.md): `/api/v1/`, сторінка кабінету
продавця з API-ключем, cron вебхуків, staging у Docker. Перевірена з цим модулем на копії БД порталу,
на продакшн ще не встановлена.

Поки API не встановлено, модуль можна використовувати в режимі **«Фід»**: портал завантажує XML за
посиланням, а замовлення надсилає вебхуком (див. API.md).

## Встановлення

1. Архів `allmarketsync-1.1.0.zip` (для PrestaShop 1.6 — `allmarketsync-1.1.0-ps16.zip`) →
   **Модулі → Менеджер модулів → Завантажити модуль** (у 1.6: **Модулі → Додати новий модуль**).
2. **Налаштувати**:
   - *Підключення*: режим обміну, URL API, ID продавця, API-ключ → **Перевірити з'єднання**.
   - *Вивантаження каталогу*: мова, валюта, категорії (нічого не вибрано = весь каталог),
     комбінації, розмір фото, націнка %, відповідність категорій (`3=101` — по рядку; підкатегорії
     успадковують правило).
   - *Замовлення*: статуси для нових і оплачених замовлень (модуль створює власний статус
     «allmarket.biz: нове замовлення»), перевізник, країна за замовчуванням, чи брати ціни й
     вартість доставки із замовлення allmarket.
   - *Відповідність статусів*: який статус PrestaShop відповідає якому статусу allmarket
     (`accepted, processing, shipped, delivered, cancelled, returned`).
3. Налаштувати cron (рядки з готовими шляхами показані внизу сторінки налаштувань).

## Розміщення категорій на allmarket.biz

Панель «Розміщення категорій на allmarket.biz» на сторінці налаштувань (режим API) показує дерево категорій
магазину; модуль підтягує дерево категорій порталу (`GET /portal-categories`, кешується на 6 год, кнопка
«Оновити категорії з allmarket.biz»). Для кожної категорії магазину можна обрати категорію порталу і спосіб:

- **Відповідає категорії порталу** (`id=X`) — товари й підкатегорії йдуть в обрану категорію порталу;
  наприклад, «Харчове обладнання» в корені магазину → «Обладнання > Промислове обладнання > Харчове обладнання».
- **Створити всередині** (`id>X`) — категорія магазину створюється як підкатегорія обраної.

Рядки без вибору йдуть за батьківською категорією, верхній рівень без вибору — у корінь порталу. Відсутні
на порталі підкатегорії створюються автоматично. Після зміни розміщення портал переносить створені ним раніше
категорії разом із товарами, а порожні видаляє, — повторно вивантажувати товари не потрібно. Галочка «Одразу
надіслати каталог» запускає задачу `catalog` одразу після збереження.

## Розклад

CLI (рекомендовано — без обмежень часу HTTP-запиту):

```
*/15 * * * *  php /шлях/до/prestashop/modules/allmarketsync/cli.php offers
*/5  * * * *  php /шлях/до/prestashop/modules/allmarketsync/cli.php orders && php /шлях/до/prestashop/modules/allmarketsync/cli.php statuses
30   3 * * *  php /шлях/до/prestashop/modules/allmarketsync/cli.php catalog
```

Або URL: `https://shop.ua/index.php?fc=module&module=allmarketsync&controller=cron&token=…&task=offers`
(посилання з токеном — у налаштуваннях модуля).

| задача | що робить |
|---|---|
| `catalog` | повна перевірка: категорії, нові/змінені картки, ціни/залишки, зняття зниклих; у режимі «Фід» — перебудова обох фідів |
| `offers` | ціни й наявність (нові позиції надсилаються повністю), зняття зниклих; фід цін |
| `orders` | імпорт нових замовлень і застосування статусів з порталу |
| `statuses` | повторне надсилання статусів, які не дійшли (портал був недоступний) |
| `feed` | перебудова XML-фідів |
| `all` | `offers` + `orders` + `statuses` |

Параметри CLI: `--force` (надіслати все й пропустити захист від масового видалення),
`--shop=ID` (мультимагазин), `-v` (лог у консоль).

## Як це працює

**Зміни визначаються за хешами.** Для кожної позиції модуль зберігає хеш картки й хеш
ціни/залишку (`ps_allmarket_offer`) і надсилає тільки змінене. Тому ловляться й зміни з імпорту
CSV, ERP чи прямого SQL, які оминають хуки PrestaShop. Повний прохід по 47 демо-товарах — ~0,1 с,
без змін запити до API не надсилаються.

**Захист від масового видалення.** Якщо за запуск зникає понад половину позицій (і більше 20) —
наприклад, через помилку у фільтрі категорій — модуль нічого не знімає і пише попередження.

**Замовлення.** Покупець шукається за email (або створюється гість; без email —
`am-<id>@allmarket.invalid`), створюється адреса, кошик, ціни фіксуються ціною з allmarket
(тимчасова специфічна ціна для кошика), замовлення створюється через `validateOrder`, потім
підставляється вартість доставки з порталу. Повідомлення до замовлення містить номер allmarket,
службу доставки, відділення, оплату, телефон і коментар. На сторінці замовлення в адмінці — блок
«allmarket.biz» зі статусом синхронізації.

Повторні спроби безпечні: якщо створення перервалося після запису замовлення, наступна спроба
прив'яже вже створене замовлення, а не створить дубль. Після 5 невдалих спроб замовлення чекає
кнопки «Повторити невдалі замовлення».

**Статуси.** При зміні статусу замовлення з allmarket модуль одразу надсилає відповідний статус
(одна спроба, щоб не гальмувати адмінку); якщо не вдалося — ставить у чергу для задачі `statuses`.
Зміна ТТН теж надсилається. Статуси з порталу застосовуються за тією ж таблицею у зворотному
напрямку (без «відкату» до вже пройденого статусу і без луни назад на портал).

## Особливості збірки для PrestaShop 1.6

- Блок «allmarket.biz» на сторінці замовлення виводиться через хук `displayAdminOrder`.
- Таблиці модуля створюються в `utf8` (старі MySQL не знають `utf8mb4`).
- Пароль створеного покупця хешується `Tools::encrypt()`; код сумісний з PHP 5.6
  (без `random_bytes`, `??` тощо).
- У 1.6 за замовчуванням вимкнено гостьове оформлення — тоді покупець з allmarket створюється
  звичайним зареєстрованим клієнтом з випадковим паролем (так само поводиться й основна збірка).
- Товар без залишку, для якого заборонено замовлення без наявності, у 1.6 не додається в кошик —
  замовлення з таким товаром потрапить у журнал з помилкою «Cannot add … to cart».

## Журнал і діагностика

Внизу сторінки налаштувань — стан (скільки позицій на порталі, скільки замовлень, результати
останніх запусків) і журнал з помилками по кожній позиції/замовленню.

Типові проблеми:

- *«carrier #N was not applied»* — перевізник не обслуговує зону країни доставки або діапазони
  ваги/ціни. Призначте перевізнику зону (наприклад, «Europe (non-EU)» для України).
- *«Currency XXX is not enabled»* — увімкніть валюту замовлення в магазині.
- *«Product not found»* — у замовленні `external_id`/`sku`, яких немає в магазині.

## Тестування

Перевірено на PrestaShop 8.2.8 (Docker, демо-дані) з мок-сервером: установка/видалення/
переустановка, повне вивантаження, дельта цін/залишків, зняття та повернення товарів, відхилені
пропозиції, імпорт замовлень (оплачені, накладений платіж, без email, неіснуючий товар,
перервана спроба), передача статусів і ТТН, черга статусів при недоступному API, вебхук
(підпис, ідемпотентність, зміна статусу), cron- і feed-URL, сторінка налаштувань, переклад.

Збірку для 1.6 перевірено на PrestaShop 1.6.1.24 / PHP 5.6.40 / MySQL 5.7 (Docker, демо-дані) за
тими ж сценаріями: установка/видалення/переустановка, каталог і дельта, імпорт замовлень з CLI та
вебхуком, статуси з ТТН і черга, cron- і feed-URL, сторінка налаштувань (збереження, перевірка
з'єднання).

Виправлення, знайдені на 1.6 (гостьові покупці, захищений `SpecificPrice::flushCache()`,
EAN «0» у комбінаціях, прибирання тимчасових цін після перерваної спроби), внесено в обидві збірки;
основну після них перевірено лише лінтером (PHP 7.2 і 8.2), повторно на PrestaShop 8 не запускали.

На PrestaShop 1.7.x і 9.x модуль не запускався — синтаксис перевірено для PHP 7.2 і 8.2.

Локальний мок:

```
MOCK_API_KEY=test-key php -S 0.0.0.0:8099 tools/mock_allmarket.php
```
